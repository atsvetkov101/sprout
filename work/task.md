## Проект

Проектирование и реализация системы с использованием DDD

Цель:

В проектной работе вы закрепите и продемонстрируете полученные на курсе знания, умения и навыки с помощью проектирования и реализации системы на основе DDD, включая стратегическое и тактическое моделирование, интеграцию контекстов и обеспечение надежности асинхронного взаимодействия. Также попрактикуете навыки командной работы (проект можно выполнять в командах по 2-3 человека) и подготовите портфолио для работодателя.

Описание/Пошаговая инструкция выполнения домашнего задания:

**Инструкция:**

**Выбор предметной области:**

Для выполнения проекта вы можете выбрать свой рабочий проект (рекомендуется) или использовать предложенный типовой домен: «Платформа доставки еды (Food Delivery)».

Бизнес-процесс Food Delivery включает в себя: регистрацию клиентов и ресторанов, просмотр меню, корзину, оформление заказа, проведение онлайн-оплаты, передачу заказа на кухню (ресторану), поиск курьера и отслеживание доставки.

**Выбор тема проектной работы:**: Система управления разъездными сотрудниками

**Этап 1: Стратегическое проектирование.**

Цель: Определить ландшафт системы, выделить границы и договориться о языке.

1.  Субдомены и инвестиции:

-   Выделите 4-5 субдоменов вашей системы.
-   Классифицируйте их (Core, Supporting, Generic). Обоснуйте, почему именно выбранный вами Core-субдомен является конкурентным преимуществом бизнеса.

2.  Единый язык (Ubiquitous Language):

-   Составьте глоссарий из 10-15 ключевых терминов для вашего Core-субдомена.
-   Укажите термин, его строгое определение в рамках контекста и недопустимые синонимы.

3.  Карта контекстов (Context Map):

-   Разбейте систему на Ограниченные контексты (Bounded Contexts).
-   Нарисуйте Карту контекстов (Miro, draw.io, PlantUML).
-   Укажите паттерны интеграции (Customer-Supplier, ACL, Conformist, Partnership и т.д.) и направления зависимости (Upstream/Downstream).
-   Объясните выбор паттернов для 2-3 самых важных связей.

**Этап 2: Тактическое проектирование ядра.**

Цель: Спроектировать богатую доменную модель (Rich Domain Model) для одного из Core-контекстов.

Выберите один Ограниченный контекст (например, Управление Заказами \\ Order Management) и выполните для него дизайн:

1.  Объекты-значения (Value Objects):

-   Выделите минимум 2 концепции, которые нужно реализовать как Value Object (например, Money, DeliveryAddress, PhoneNumber).
-   Код: Напишите реализацию одного VO на вашем языке программирования (с проверкой инвариантов и структурным равенством).

2.  Сущности и Агрегаты (Entities & Aggregates):

-   Спроектируйте Корень Агрегата (Aggregate Root). Определите его внутренние сущности.
-   Код: Реализуйте этот агрегат. Скройте сеттеры, реализуйте бизнес-метод изменения состояния (например, Order.AddItem или Order.Confirm), который защищает бизнес-правила (инварианты).

3.  Доменные сервисы (Domain Services):

-   Выявите бизнес-правило, которое не ложится ни в один агрегат (например, расчёт скидки с участием внешнего промо-движка или проверка лимитов).
-   Напишите сигнатуру (или псевдокод) Доменного сервиса для этого правила.

**Этап 3: Архитектура приложения и Паттерны.**

Цель: Инкапсулировать доменную модель и подготовить её к работе с внешним миром.

1.  Гексагональная архитектура (Ports and Adapters):

-   Опишите структуру директорий/пакетов для выбранного контекста.
-   Код: Напишите интерфейс исходящего порта (например, IOrderRepository) и входящего порта (Use Case / Application Service).

2.  Репозитории и Фабрики:

-   Код: Напишите доменную Фабрику для создания сложного Агрегата (со всеми проверками).

3.  CQRS:

-   Опишите, для какого экрана/запроса в вашем контексте имеет смысл разделить Command и Query модели.
-   Приведите DTO для чтения (Read Model) и опишите стек: какую БД вы выберете для Command-модели (например, PostgreSQL), а какую для Query-модели (например, Redis, ElasticSearch или отдельная денормализованная таблица). Объясните механизм их синхронизации.

4.  API Gateway / BFF (Опционально):

-   Опишите, как внешние клиенты (Web, Mobile) будут взаимодействовать с вашими микросервисами.
-   Нужен ли вам единый API Gateway или паттерн Backend-for-Frontend.

**Этап 4: Асинхронность, Базы данных и Интеграция.**

Цель: Связать контексты между собой, обеспечив надёжность и согласованность данных.

1.  Доменные и Интеграционные события (Domain & Integration Events):

-   Спроектируйте событие, которое генерируется вашим Агрегатом (например, OrderPlacedDomainEvent).
-   Покажите, как оно трансформируется в OrderPlacedIntegrationEvent для отправки в брокер сообщений (Kafka/RabbitMQ).
-   Опишите структуру JSON payload.

2.  Надёжная публикация (Transactional Outbox):

-   Опишите алгоритм или приведите схему того, как вы решите проблему Dual Write (сохранение агрегата в БД + отправка события в брокер) с помощью паттерна Transactional Outbox.
-   Укажите инструмент, который будет читать таблицу Outbox (например, Debezium (CDC), Kafka Connect, или кастомный Polling Publisher).

3.  Распределённые транзакции (Saga):

-   Распишите шаги Саги (Saga) для сложного бизнес-процесса, затрагивающего минимум 3 контекста (например: Заказ -> Оплата ->Доставка).
-   Обязательно опишите компенсирующую транзакцию: что произойдёт, если на третьем шаге система ответит ошибкой (как вернутся деньги и изменится статус заказа).

4.  Проектирование хранилища (Базы данных):

-   Выберите конкретную СУБД (PostgreSQL, MongoDB, etc.) для вашего агрегата и обоснуйте выбор.
-   Приведите DDL-скрипты (CREATE TABLE) или структуру JSON-документа для сохранения всего агрегата (Корня, его внутренних сущностей и Value Objects).

5.  Топология брокера сообщений:

-   Для RabbitMQ: опишите структуру Exchanges, Routing Keys и Queues для ваших событий.
-   Для Kafka: укажите названия Topics, количество партиций, ключ партиционирования (Partition Key, например OrderId) и Consumer Groups.

**Этап 5: Наблюдаемость и Деплой.**

Цель: Подготовить систему к эксплуатации в Production.

1.  Логирование и Трассировка:

-   Приведите пример идеального структурированного JSON-лога, который генерируется при успешной отработке Use Case из Этапа 3.
-   Обязательно включите CorrelationId.

2.  Миграция БД (Zero-Downtime):

-   Опишите шаги миграции по паттерну Expand-Contract для одного из частых рефакторингов (например, переименование колонки или вынос поля в новую таблицу) без остановки микросервиса.

**Задание со звездочкой (\*)**

Для тех, кто хочет получить максимум практического опыта и настроить реальную инфраструктуру.

1.  Infrastructure as Code (Docker Compose):

-   Создайте файл docker-compose.yml, который локально поднимает: выбранную вами базу данных, брокер сообщений (RabbitMQ или Kafka) и инфраструктуру для observability (например, Jaeger + Prometheus + Grafana).

2.  Реализация Outbox Worker:

-   Напишите работающий фоновый процесс (Background Worker), который с заданной периодичностью читает записи из таблицы Outbox в вашей БД и реально публикует их в поднятый в Docker брокер сообщений.
-   Аналогично, можно сделать отдельный микросервис мониторинга нагрузки (сколько заказов за сегодня или за текущий час) или сколько выручки за сегодня.

**Формат сдачи проекта:**

Проект сдаётся в виде репозитория на GitHub, который должен содержать:

1.  README.md - основной документ с описанием архитектуры (Этапы 1, 3, 4, 5). Все схемы, глоссарий и архитектурные решения описываются здесь текстом или вставляются картинками.

2.  Папка src/ - исходный код Тактического проектирования (Этап 2 и часть Этапа 3). Не нужно писать весь микросервис и подключать фреймворки. Достаточно реализовать «чистую» часть гексагона (Domain и Application слои): классы Агрегатов, Value Objects, Интерфейсы репозиториев, Фабрики и 1-2 Use Case.

3.  Дополнительное задание (по желанию): В процессе проверки проекта преподаватель может предложить новый сценарий развития бизнес-требований. Вам потребуется описать, как ваша текущая архитектура адаптируется к этим изменениям (или какие потребуются доработки), чтобы
    на практике продемонстрировать её гибкость.
